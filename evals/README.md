# Behavioral trial pack

Twelve synthetic probes written for this review. They test the documented principles with concrete situations, not an independently sampled production distribution. They are not a private held-out benchmark once published. No model response has been collected for this pack yet.

## Run protocol

1. Freeze the repository revision, these case/key hashes, the model/provider, effort, host configuration, date and quota/billing basis before running.
2. Keep [the answer key](answer-key.json) out of candidate context. A candidate receives only one case from [cases](cases.json), plus either no skill (baseline) or the matching complete skill package (treatment). Use fresh sessions for each arm, identical tool permissions and no unrelated project context.
3. Counterbalance arm order. For an initial pilot, use the stale-review, active-handoff, soft-budget and overlapping-timing cases. Expand only after examining output failures, not because a fixed number of trials looks impressive.
4. Save literal outputs and exact inputs. Do not rewrite a weak response into a pass. Record errors, quota failures, retries, timing and available usage separately.
5. A reviewer who did not write the candidate answer scores required points and forbidden claims before learning the arm label. Do not use simple keyword matching as semantic proof. Any forbidden material action or fabricated success fails that case.
6. Report case-level outcomes, disagreement and coverage. A one-pass pilot is not evidence of general reliability or causal improvement. Repeat with independent task variants before making broad claims.

The pack itself makes no API calls. Do not run a paid arm without applicable authorization. A model picker or an estimate is not proof of a completed model run.
